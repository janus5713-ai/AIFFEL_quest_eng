# Day 7 프로젝트 2 제출 기록 

## 0. 프로젝트 개요

이번 프로젝트는 **AI 챗봇을 웹에서 사용할 수 있게 만드는 실습**이다.

노트북에서만 모델을 실행하는 것이 아니라, 다음 흐름으로 동작하게 만들었다.

```text
사용자
↓
Streamlit 화면에서 질문 입력
↓
FastAPI 서버로 질문 전송
↓
AI 모델이 답변 생성
↓
Streamlit 화면에 답변 표시
```

주요 파일은 다음과 같다.

| 파일 | 하는 일 |
|---|---|
| `app/chatbot_model.py` | AI 모델을 불러오고 답변을 만든다 |
| `app/chatbot_schemas.py` | 사용자가 보낼 데이터 형식을 정한다 |
| `app/chatbot_api.py` | 질문을 받는 API 서버를 만든다 |
| `frontend/app_chatbot.py` | 사용자가 보는 채팅 화면을 만든다 |

### 1.1 GPU / PyTorch 환경 확인

**캡처 파일 예시:** `screenshots/01_gpu_check.png`

처음에는 PyTorch가 CPU 버전으로 설치되어 있었다.


이 상태에서는 컴퓨터에 RTX 3070 그래픽카드가 있어도 AI 모델이 GPU를 사용하지 못한다.

```text

```

**설명:**  
AI 챗봇 모델은 계산량이 많다. CPU로 실행하면 매우 느리기 때문에 GPU가 제대로 잡혔는지 먼저 확인했다. GPU가 잡히지 않으면 서버가 실행되지 않도록 설정했다.

## 2.2 모델 준비 체크포인트

### Q1. `encode()`와 `decode()`는 각각 무엇을 합니까?

`encode()`는 사람이 쓴 문장을 모델이 읽을 수 있는 숫자로 바꾼다.

```text
"안녕하세요" → [숫자, 숫자, 숫자]
```

`decode()`는 모델이 만든 숫자를 다시 사람이 읽을 수 있는 문장으로 바꾼다.

```text
[숫자, 숫자, 숫자] → "안녕하세요"
```

---

### Q2. `temperature`는 답변에 어떤 영향을 줍니까?

`temperature`는 모델 답변의 자유도를 정하는 값이다.

값이 낮으면 답변이 더 안정적이다.  
값이 높으면 답변이 다양해질 수 있지만, 엉뚱한 말을 할 가능성도 커진다.

이번 프로젝트처럼 정확한 답변이 중요한 경우에는 낮은 값이 더 적합하다.

```text
낮은 temperature: 안정적이지만 단조로움
높은 temperature: 다양하지만 헛소리 가능성 증가
```

---

### Q3. 여러 번 대화할 때 이전 대화 기록을 같이 보내는 이유는 무엇입니까?

AI 모델은 기본적으로 이전 요청을 자동으로 기억하지 않는다.

따라서 사용자가 이전에 무슨 말을 했는지 알려주려면, 이전 대화 기록을 매번 같이 보내야 한다.

예를 들어 사용자가 이렇게 물었다고 하자.

```text
사용자: 마리 퀴리는 누구야?
챗봇: 노벨상을 받은 과학자입니다.
사용자: 그 사람은 뭘 발견했어?
```

마지막 질문만 보내면 모델은 “그 사람”이 누구인지 모를 수 있다.  
그래서 이전 대화까지 같이 보내야 자연스럽게 이어서 답할 수 있다.

## 2.3 FastAPI 서버 체크포인트

### Q1. `messages`가 리스트인 이유는 무엇입니까?

챗봇은 한 문장만 받는 것이 아니라 여러 번의 대화를 처리해야 한다.

그래서 `messages`를 리스트로 만들었다.

예시는 다음과 같다.

```json
[
  {"role": "user", "content": "안녕하세요"},
  {"role": "assistant", "content": "안녕하세요. 무엇을 도와드릴까요?"},
  {"role": "user", "content": "오늘 뭐 하면 좋을까?"}
]
```

이렇게 하면 이전 대화까지 한 번에 서버로 보낼 수 있다.

---

### Q2. 서버가 대화 기록을 저장하지 않고, 사용자가 매번 전체 기록을 보내는 이유는 무엇입니까?

서버를 단순하게 만들기 위해서다.

서버가 모든 사용자의 대화를 직접 저장하면 관리가 복잡해진다.

- 사용자별 대화 저장 필요
- 서버 메모리 관리 필요
- 서버가 여러 대일 때 기록 공유 필요
- 서버가 꺼졌을 때 복구 문제 발생

그래서 이번 프로젝트에서는 화면 쪽에서 대화 기록을 가지고 있다가, 질문할 때마다 전체 기록을 서버에 보내는 방식을 사용했다.

---

### Q3. `max_new_tokens`를 너무 크게 하면 어떤 문제가 생깁니까?

`max_new_tokens`는 모델이 새로 만들 수 있는 답변 길이를 정하는 값이다.

이 값을 너무 크게 하면 문제가 생긴다.

- 답변 시간이 길어진다
- GPU 메모리를 더 많이 쓴다
- 답변이 불필요하게 길어진다
- 질문과 상관없는 말이 이어질 수 있다

짧은 질문에는 짧은 답변 길이를 주는 것이 좋다.

---

## 2.4 Streamlit 화면 체크포인트

### Q1. `st.chat_message`와 `st.chat_input`은 각각 무엇입니까?

`st.chat_message`는 채팅 말풍선을 화면에 보여주는 기능이다.

`st.chat_input`은 사용자가 질문을 입력하는 입력창이다.

쉽게 말하면 다음과 같다.

```text
st.chat_message = 채팅 내용 보여주기
st.chat_input = 질문 입력창
```

---

### Q2. `st.session_state["chat_messages"]`에 대화 기록을 저장하는 이유는 무엇입니까?

Streamlit은 사용자가 버튼을 누르거나 메시지를 입력할 때마다 코드가 다시 실행된다.

일반 변수에 대화 기록을 저장하면 다시 실행될 때 기록이 사라진다.

그래서 `st.session_state`에 저장한다.  
이렇게 하면 화면이 다시 실행되어도 이전 대화가 유지된다.

---

### Q3. “대화 초기화” 버튼에서 `st.rerun()`을 쓰는 이유는 무엇입니까?

대화 기록을 지운 뒤 화면을 바로 새로 고치기 위해서다.

대화 기록을 비운 다음 `st.rerun()`을 실행하면 화면이 다시 그려지고, 이전 대화가 사라진 상태가 바로 보인다.

## 3. 프로젝트 회고

이번 프로젝트에서 가장 크게 느낀 점은 **모델을 실행하는 것과 서비스를 만드는 것은 다르다**는 점이다.

노트북에서 `model.generate()`를 실행하는 것은 비교적 단순하다.  
하지만 실제 사용자가 웹 화면에서 질문하고 답변을 받게 만들려면 더 많은 요소가 필요했다.

필요했던 요소는 다음과 같다.

- 서버 만들기
- 입력값 검사하기
- API Key로 인증하기
- 에러 처리하기
- 채팅 화면 만들기
- 이전 대화 기록 유지하기
- GPU 사용 여부 확인하기

특히 GPU 환경 설정이 중요했다. 처음에는 CPU용 PyTorch가 설치되어 있어서 RTX 3070이 있어도 GPU를 사용하지 못했다. CUDA용 PyTorch를 설치하고 `torch.cuda.is_available()`이 `True`인지 확인한 뒤에야 GPU에서 모델을 실행할 수 있었다.

또한 작은 언어 모델의 한계도 확인했다. `Qwen2.5-3B-Instruct` 모델은 실습용 챗봇으로는 사용할 수 있지만, 정확한 사실 질문에는 틀린 답을 할 수 있었다. 그래서 실제 서비스에서는 더 좋은 모델을 쓰거나, 근거 문서를 찾아서 답하게 만드는 방식이 필요하다고 느꼈다.

이번 프로젝트에서 개선할 점은 다음과 같다.

1. 더 좋은 모델 사용하기
2. 모델이 틀린 내용을 말하지 않도록 근거 문서 연결하기
3. 서버 설정을 `.env` 파일로 분리하기
4. Docker로 실행 환경을 고정하기
5. 답변 시간이 너무 길어지지 않도록 제한하기
6. 에러가 났을 때 화면에 더 쉽게 설명하기

최종적으로 이번 프로젝트는 AI 모델을 단순히 실행하는 것을 넘어, 웹 화면과 API 서버를 연결해 하나의 챗봇 서비스로 만드는 경험이었다. 모델 배포에서는 모델 자체뿐 아니라 실행 환경, 인증, 에러 처리, 화면 구성, 테스트가 모두 중요하다는 점을 배웠다.
